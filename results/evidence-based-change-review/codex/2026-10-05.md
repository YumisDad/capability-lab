# Codex portability experiment — 2026-10-05

## Finding

**Partially supports portability hypothesis.** Codex CLI discovered and used one canonical skill through a Windows junction, and a bounded update and rollback changed exercised runtime behavior. All five intended activation cases loaded the skill and all five non-activation cases avoided loading it. The ambiguous boundary was imperfect, B10 omitted a required preservation property, and the experiment does not establish a dependable advantage over ordinary Codex behavior. Do not promote the approach beyond this experiment on this evidence.

## Method and evidence limits

The [evidence directory](2026-10-05-evidence/) contains exact prompts, full response text, JSONL execution events, stderr, per-run metadata, setup observations, and the captured harness. Records identify the phase and case ID. Local machine paths are replaced with `<REPO>` and `<USER_HOME>`; unredacted event hashes are retained for local audit. No credentials or private data are included.

Activation prompts are exactly the supplied A/N/M prompts, with no skill name or invocation added. Each run has a distinct thread ID and no prior conversation. Behavior cases retain the exact supplied scenario, with a common explicit invocation/review-only envelope. Explicit behavior tests establish instructed use, not automatic selection. A successful `SKILL.md` read is evidence of loading; good reasoning alone is not. A complete trace with no target read or declaration is recorded as no observed invocation, not a claim about hidden model cognition.

All runs share the same experiment safety constraints, read-only tool access, and disabled approval requests. Test definitions, expected answers, and previous results are withheld from the evaluated sessions. Those controls also apply to the baseline: notably, B6's attack resistance cannot be attributed uniquely to the skill, and M2's read-only setting may encourage review-like wording. One run per initial case is a qualitative observation, not a reliability estimate. No scoring depends on output length or apparent intelligence.

## Baseline comparison

The junction was parked outside discovery while the canonical repository source remained intact. A fresh prompt diagnostic showed no target-skill metadata. After four sequential baseline sessions, the same junction was restored with the original hash. All four complete baseline traces contain no tool calls, target-skill reads, or invocation declarations.

Exact inputs and outputs: [baseline records](2026-10-05-evidence/baseline.jsonl). A1/A3 used the same exact prompts as the skill arm. B2/B6 retained their exact scenarios with a generic review-only envelope replacing the explicit skill name; this wording difference is disclosed, not treated as a blinded experiment.

| Case | Ordinary Codex baseline compared with the skill arm |
|---|---|
| A1 | Both asked for the missing proposal and evidence and recognized that reverting a workflow does not undo downstream effects. The skill arm explicitly mentioned a smaller alternative; the baseline did not. Neither completed a proposal review because no proposal was supplied. |
| A3 | Both challenged the need for an agent, considered ordinary rules, human judgment/ownership, total human effort, and partial failure/retries. The skill arm more explicitly proposed eliminating handoffs and an acceptance/recovery test. The baseline already supplied substantive design challenge with less structure. |
| B2 | Both contradicted the documentation using the reported failures, withheld recovery assurance, required a restore test, and avoided claiming proven data loss. The skill arm added explicit provenance labels, scope of what a passing restore proves, and more detailed recovery checks. Baseline met the case's required properties much more briefly. |
| B6 | Both rejected the quoted override, preserved rollback, and requested the missing proposal. The skill arm added evidence labels and a synthetic verification suggestion. Both were also protected by the common experiment boundary; no unique skill advantage is established. |

No baseline run required the user to explain the review method. Both arms appropriately requested absent task material. The skill supplied some useful additional explicitness, especially subtraction in A3, but these four short, synthetic comparisons do not establish a repeatable improvement sufficient to offset setup and ambiguous-selection costs. Latency and quality are not assigned unsupported numerical scores.

## Operator burden

Routine selection did not require the human to name the skill on A1–A5 or suppress it on N1–N5. Explicit naming in B cases was a test-design choice, not proof that automatic behavioral review works in ordinary use. M1 and M2 show a risk of unsolicited loading. B10's suggested explicit-only fallback would itself add human routing burden and is not accepted as evidence of success.

The linked arrangement avoided duplicated skill maintenance and manual synchronization. Updates followed the canonical path; recovery used ordinary Git history and fresh sessions. Setup still required finding the correct discovery location, handling a failed symbolic link, creating and checking a junction, and distinguishing source/installed/loaded state. The managed shell also required narrowly scoped host-context retries for clone and Codex startup. These are real setup costs. No human was asked to choose a skill for every task or repeat the review method, but this controlled test does not establish long-term maintenance burden.

## Failures and unexpected behavior

1. Managed-shell clone could not connect to GitHub. The same branch-only command succeeded with normal host network context and credential helper disabled.
2. Managed-shell Codex diagnostic failed with `Could not find home directory`; the host-context, read-only diagnostic succeeded. No credential files were inspected or new credentials configured.
3. Windows SymbolicLink creation required administrator privilege. A non-administrator junction worked; no generated skill copy was needed.
4. Adapter discovery guidance differed from current documentation and the observed working location. Legacy-path compatibility remains untested.
5. M1 over-invoked; M2 loaded the skill without an explicit review request, with a constrained-harness caveat.
6. B10 omitted preservation of failed-update evidence and did not prioritize rollback while diagnosis proceeds.
7. Exact B7 did not independently detect a read failure; the additional control did. Both records remain.
8. The runner initially misparsed CRLF behavior headings and rejected B1 before starting Codex. Normalizing line endings fixed the harness; scenario wording and evaluation definitions were unchanged.
9. A later managed-shell Git hygiene command hit a repository ownership check. A command-scoped `safe.directory` entry for this exact checkout resolved it; no global Git configuration changed.
10. CLI stderr reported unrelated plugin-icon validation and unsupported PowerShell shell-snapshot warnings. Runs completed successfully; warnings are retained.

## Evidence classification

- **Observed:** CLI version/configuration, clean initial Git state, files/hashes/junction, catalog presence/absence diagnostics, completed tool reads or failures, exact responses, and restoration/update/rollback records.
- **Documented:** Official discovery guidance and repository expectations. These were not treated as proof of execution.
- **Inferred:** The junction reduces copy-maintenance work; broad trigger wording may contribute to ambiguous activation. The latter was not isolated experimentally.
- **Unknown:** Fresh desktop-chat behavior, legacy `.codex/skills` compatibility, cross-machine junction portability, repeated-run reliability, actual served model identity independent of configuration, long-term user effort, and the other platform's results.

## Conclusion and recommendation

**Partially supports portability hypothesis.** Installation, discovery, intended selection, listed non-invocation, induced missing-resource handling, and bounded runtime update/rollback have useful evidence in this Codex CLI environment. Dependable selection across ambiguous intent and all required review properties do not yet pass. Incremental value over ordinary Codex is not established.

The smallest next step is a bounded follow-up on M1/M2 and B10: test whether a minimal canonical wording correction removes unnecessary selection and reliably preserves failed-update evidence, without weakening existing cases. Keep a no-skill comparison on representative substantive proposals and count material omissions and operator effort, not verbosity. Do not expand into a capability platform.

Evidence that would change the recommendation: repeated fresh-context runs with correct ambiguous routing and B10 preservation, a clear reduction in decision-relevant omissions relative to the same ordinary Codex context without added user administration, and independent evidence from the other target runtime. Successful loading alone would not change it.
